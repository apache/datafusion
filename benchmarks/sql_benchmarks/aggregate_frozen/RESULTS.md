# Frozen final aggregation experiment

This experiment starts from DataFusion PR #25724 at `f9df89e2b1077deaae9be106682c9f1e4d0d61d2`. The benchmark data is generated by `range()`; no ClickBench `hits.parquet` or `hits_partitioned` dataset was available in the local workspace. These results do not establish an outcome for ClickBench Q11, Q12, Q14, Q18, Q33, or Q34. The ClickBench runner maps query number `N` to `queries/qN.sql`, starting at `q0.sql`.

The experiment uses `hash_aggregate_bucket_threshold=4000`. Its optional `hash_aggregate_bucket_adaptive=true` retains the frozen table and probes subsequent rows against its original keys. Hits merge into that table, misses enter buckets, and the frozen state enters the buckets at EOF. This last merge preserves correctness after bypass sends later occurrences of frozen keys to buckets. Each partition samples 65,536 post-freeze rows and bypasses the probe when fewer than 25% hit. The sample is one-shot; it does not reactivate probing after a distribution change.

The current DataFusion `GroupValues` interface has no lookup-only operation. This implementation therefore materializes a second encoded-key index with `RowConverter` and `HashSet`, then calls the original aggregation method for hit rows. Unlike the upstream [ClickHouse design](https://github.com/ClickHouse/ClickHouse/blob/master/src/Interpreters/AdaptiveAggregation.h) and its [producer state](https://github.com/ClickHouse/ClickHouse/blob/master/src/Interpreters/AdaptiveAggregationImpl.h), it does not reuse the table or routing hash for the first probe. The additional encoding and gathering work is part of the measured result.

## Reproduce the SQL comparison

Build with `cargo build -p datafusion-benchmarks --release --bin benchmark_runner`. From the repository root, run the following commands with the same host and no other benchmark workload running:

```bash
DATAFUSION_EXECUTION_HASH_AGGREGATE_BUCKET_THRESHOLD=0 \
  target/release/benchmark_runner aggregate_frozen --iterations 10 --partitions 12
DATAFUSION_EXECUTION_HASH_AGGREGATE_BUCKET_THRESHOLD=4000 \
  target/release/benchmark_runner aggregate_frozen --iterations 10 --partitions 12
DATAFUSION_EXECUTION_HASH_AGGREGATE_BUCKET_THRESHOLD=4000 \
DATAFUSION_EXECUTION_HASH_AGGREGATE_BUCKET_ADAPTIVE=true \
  target/release/benchmark_runner aggregate_frozen --iterations 10 --partitions 12
```

The six SQL files each consume 2.4 million generated rows. Q01/Q04 have 80% hot keys and 20% unique keys; Q02/Q05 have five rows per key; Q03/Q06 are near unique. Q04-Q06 use approximately 80-character string prefixes. All six plans were checked to contain `AggregateExec: mode=FinalPartitioned`, and `EXPLAIN ANALYZE` showed 12 final bucket splits for each bucket-enabled query.

### Optimized build, median of iterations 1-9, milliseconds

| Query                       | Bucketing off | Original buckets | Frozen experiment | Frozen / original |
| --------------------------- | ------------: | ---------------: | ----------------: | ----------------: |
| Q01 hot integer             |           6.9 |             10.6 |              11.9 |             1.12x |
| Q02 uniform integer         |          12.8 |             13.8 |              16.7 |             1.21x |
| Q03 near unique integer     |          16.2 |             14.5 |              17.1 |             1.18x |
| Q04 hot long string         |          29.6 |             35.1 |              41.2 |             1.17x |
| Q05 uniform long string     |          57.5 |             64.3 |              70.3 |             1.09x |
| Q06 near unique long string |          64.4 |             72.3 |              77.4 |             1.07x |

The original buckets beat the single table only for Q03 in this suite. The frozen experiment was slower than the original buckets on all six queries. These queries are short, and their source and output costs differ from ClickBench; the comparison is evidence about this implementation on these distributions, not about the real ClickBench queries.

The final input is already reduced by the partial stage. Q02/Q05 therefore remove only about 4% of staged rows before bypass, and Q03/Q06 remove none. Q01/Q04 remove about 20%, but still spend more CPU in the extra lookup and row gathering. `bucket_routing_time` is summed CPU time across final partitions. `bucket_tail_time` sums each partition's wall time from input EOF through output completion; it is not query-wide wall latency. These metrics were collected with the development CLI build in a separate run and must not be added to or directly compared with the optimized benchmark milliseconds.

The ignored Rust diagnostic `final_hash_aggregate_frozen_table_diagnostics` can print exact counters with `DATAFUSION_BUCKET_DIAGNOSTICS=1 cargo test -p datafusion-physical-plan final_hash_aggregate_frozen_table_diagnostics --lib -- --ignored --nocapture`. Its ordered repeated-key case sampled only 6,144 hits in 65,536 rows (9.375%) and bypassed before later repeats arrived. That demonstrates a possible sampling phase bias; it does not predict the ClickBench hit rate.

## Assessment

This version should remain an experiment. Before proposing it for merge, a direct lookup-only `GroupValues` path and reuse of the routing hash would remove two measured costs; a later measurement could then isolate the benefit of retaining frozen state. The one-shot sample also needs testing against changing key distributions. Real ClickBench Q11/Q12/Q14 and Q18/Q33/Q34, with Jay's dataset and threshold of 262,144, remain the decision point.
