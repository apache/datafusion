# Implementation Status

This file tracks which checks from [CHECKS.md](CHECKS.md) are implemented.
Update it in the same change that adds or extends a check.

Status values:

- **Done**: implemented as described in the catalog, with tests.
- **Partial**: implemented, but part of the catalog entry is missing. The
  notes say what is missing.
- **Pending**: not implemented.

## Built-in plans covered

`tests/physical_plan/builtin_plans/` describes each of these plans as a
`PlanFactory`, checks it with the `PlanHarness` on the cases of
`Profile::defaults` (and also of `Profile::extended` with the `extended_tests`
feature), and records the findings in
`tests/physical_plan/builtin_plans/snapshots/`, one snapshot per family:
`physical_plan__builtin_plans__builtin_{plan,aggregate,join,window,source}_findings.snap`,
with an `_extended` snapshot for each. The harness gives each plan the inputs
it requires: sorted, hash partitioned or in one partition. Each factory differs
from the others in its configuration (mode, join type, fetch, filter,
`preserve_partitioning`, or an ordering in the base spec to exercise a sorted
code path), not only in how its inputs are laid out. The exchange between two
aggregation phases (`CoalescePartitionsExec` or a hash `RepartitionExec`) is
part of the plan the factory builds, as the optimizer builds it, not an input.

Simple operators (`builtin_plan_findings`, `mod.rs` and `operators.rs`):

- `EmptyExec`, `PlaceholderRowExec`
- `ProjectionExec`, with and without a literal
- `FilterExec`, with and without fetch, and on an equality, which makes a
  column constant
- `CoalesceBatchesExec`, with and without fetch
- `CoalescePartitionsExec`, with and without fetch
- `SortExec`, with and without fetch, with and without
  `preserve_partitioning`, on a nullable column, and on input that is already
  sorted (a base spec with an ordering), with and without fetch
- `SortPreservingMergeExec`, with and without fetch
- `RepartitionExec`, round robin and hash, each also preserving order on
  input sorted on `a` (a base spec with an ordering). The order preserving
  variant merges in every case but `single partition`, where the input has
  one partition, and `uniform constants`, where the ordering on a constant
  `a` is not reported and the repartition does not preserve order.
- `GlobalLimitExec`, with and without fetch, `LocalLimitExec`
- `UnionExec`
- `BufferExec`
- `CooperativeExec`
- `PartialSortExec`, `InterleaveExec`, `UnnestExec`, `AsyncFuncExec`,
  `ScalarSubqueryExec`, `OutputRequirementExec`, `AnalyzeExec`,
  `ExplainExec`, `RecursiveQueryExec`, and a `ForeignExecutionPlan` (FFI)
  wrapping a plan (`operators.rs`)

Windows (`builtin_window_findings`, `windows.rs`): `BoundedWindowAggExec` and
`WindowAggExec` with ranking, offset and aggregate window functions, in the
input order modes the optimizer chooses, and `PartitionedTopKExec`.

Sources and sinks (`builtin_source_findings`, `sources.rs`): `DataSourceExec`
over memory and over files, `LazyMemoryExec`, `StreamingTableExec`,
`DataSinkExec`, and the `DELETE` and `UPDATE` plans of a `MemTable`. Each
source is built from the rows of a generated input, and declares what the
input declares. The files of the file sources are not written, so they only
run the static checks (see the checks allowed in the audit below).

Aggregates and joins have their own snapshots. They are built the way the
physical planner and the optimizer build them (`physical_planner.rs`,
`EnforceDistribution`, `JoinSelection`, `TopKAggregation`,
`LimitedDistinctAggregation`), and the harness meets their required input
ordering and distribution:

- `AggregateExec` with `count`, `sum`, `min`, `max` and `avg`, including a
  floating point `sum` and `avg`: `Partial` and `Final` over a
  `CoalescePartitionsExec`, with and without `GROUP BY`, and with only `min`
  and `max` (which creates a dynamic filter); `Partial` and `FinalPartitioned`
  over a hash `RepartitionExec`, on unsorted input and on sorted input with an
  order preserving repartition (`InputOrderMode::Sorted` in both phases);
  `Single` with and without `GROUP BY`, on sorted input (`Sorted`) and on
  partially sorted input (`PartiallySorted`); `SinglePartitioned` on hash
  partitioned input; a TopK limit on `max` in both phases; a soft `DISTINCT`
  limit; and `ROLLUP` in both phases.
- `HashJoinExec` in `CollectLeft` mode for every join type, with a filter for
  `Inner`, `Full`, `RightSemi` and `LeftAnti`, with nulls equal, and with a
  fetch; in `Partitioned` mode, on inputs hash partitioned on the keys, for
  `Inner`, `Left`, `Full`, `RightAnti` and `LeftMark`, and `Full` with a
  filter.
- `SortMergeJoinExec` on inputs sorted and hash partitioned on the keys, for
  `Inner`, `Left`, `Full`, `LeftSemi`, `RightAnti` and `LeftMark`, and
  `Inner`, `Full` and `LeftAnti` with a filter.
- `NestedLoopJoinExec` for `Inner`, `Left`, `Full`, `RightSemi`, `LeftAnti`
  and `RightMark`, `CrossJoinExec`, `SymmetricHashJoinExec` in both partition
  modes, `PiecewiseMergeJoinExec` for `Inner`, `Full` and `RightSemi`, and
  `AsOfJoinExec`.

Join keys are nullable and drawn from small domains of different sizes on
each side, so that every join has matches, rows without a match on both
sides, and null keys. Every input row has a unique row id, added by the
harness.

Not covered yet: `SymmetricHashJoinExec` with sort expressions (pruning), dynamic
filters produced by joins (`MockSourceExec` accepts no pushed down filters,
so a hash join never gets a consumer for its filter), `PartialReduce`
aggregates, and aggregates that spill or skip partial aggregation (the
inputs are far below `skip_partial_aggregation_probe_rows_threshold`).

## Checks allowed in the audit, and check limitations

Checks allowed for a specific plan are allowed with `PlanFactory::allow`,
and listed with the reason under the plan in the snapshot. None of them
hides a real problem.

- `batch_boundary_invariance` is allowed for `AggregateExec Single with DISTINCT limit`. The soft limit set by `LimitedDistinctAggregation` stops
  the aggregate after the input batch in which it has seen enough groups, so
  how many groups it emits, and which, depends on batch boundaries
  (`aggregates/mod.rs:859-864`). Only the `LIMIT` above it makes the result
  well defined. The node reports no fetch, so a check cannot tell this from
  a node whose results depend on batching by mistake. The rows it emits do
  appear in its normal output.
- `limit_pushdown_missed` is allowed for every window operator (`windows.rs`):
  a window function can need later rows, as `LEAD`, `NTILE`, `CUME_DIST` and
  frames that end after the current row do, which A5 describes as false
  positives.
- Every check that executes the plan (every `CheckKind` but `Static`) is
  allowed for the file sources: `DataSourceExec Parquet`, `CSV`, `JSON`,
  `Arrow`, and `Parquet with projection and limit` (`sources.rs`,
  `static_checks_only`). Each is a `FileScanConfig` over one file per input
  partition, `data/part-<n>.<extension>` on the local file system, with the
  statistics of the input partition, but the files are not written. Executed,
  the plans fail because the files do not exist, and which file a run reports
  first varies. So the file sources are only checked on what they report, and
  the file readers (decoding, projection, limits, pruning) are not checked at
  runtime. To check them, write the rows of each input partition to a file in
  a temporary directory when the case is built, and point the scan at it.
- `emission_type_holds` is allowed for `FilterExec on an equality`. The
  filter keeps one row in 16 and emits batches of 8192 rows
  (`filter.rs:81`), so it needs about 131072 rows per input partition before
  it emits, more than the unbounded input of the stream experiments delivers
  (65536). This is the false positive described for B11.
- `exact_statistics_hold` checks a node whose child has a false exact
  statistic against the statistics it computes from the child's, with the
  false values replaced by the true values of the child's output. That
  output comes from executing the child on its own, so for a child whose
  output depends on timing, such as a `SortExec` with
  `preserve_partitioning` and a fetch, the corrected values can differ from
  the rows the node received. The snapshots are recorded on a
  current-thread runtime, where they do not. A node that only implements the
  deprecated `partition_statistics` and asks its children for statistics
  itself is not given the corrected values.
- Waits for streams and memory to be released end once no task is alive on
  the Tokio runtime. A plan that releases them later from a thread outside
  the runtime, for example in a `spawn_blocking` task, would be reported
  although it releases them.
- The checks that need stream experiments (`boundedness_holds`,
  `emission_type_holds`, `lazy_evaluation_holds`, `streams_released` and
  `errors_propagate`) only run in the `default` case, since they depend on
  how a plan drives its streams rather than on the shape of its data, and
  several of them wait for the stream timeout. A plan whose stream behavior
  only goes wrong with one partition, inexact statistics or empty input is
  not reported.
- Every run of a plan with side effects acts on the same state. The variant
  runs and `reset_state_reexecution` run `MemDeleteExec` again on a
  `MemTable` that its normal execution already changed, so they compare
  different deletions, and are reported (see the known findings). A factory
  for such a plan would need to rebuild its state for every run, which the
  checker cannot ask it to do.
- Each node is executed on its own, so a node that only works under its
  parent fails: the `WorkTableExec` below a `RecursiveQueryExec`, and a
  `FilterExec` with a `ScalarSubqueryExpr` below a `ScalarSubqueryExec`
  (`execution_succeeds`, see the known findings).
- The harness only meets the requirements of the nodes directly above the
  inputs, and only hard ordering requirements. A factory whose plan has a
  node with a requirement on a node the factory built itself must build that
  node so that it meets it (as the audit's two-phase aggregates do with the
  exchange between the phases), and a plan is not tested with the orderings
  it only benefits from (soft requirements), unless its base spec has them.
- Joins report `CardinalityEffect::Unknown`, so `equal_cardinality_num_rows`,
  `cardinality_effect_bounds_num_rows` and `cardinality_effect_holds` do not
  apply to them. What `Equal` or `LowerEqual` would mean for a node with two
  inputs is not defined by `ExecutionPlan`, and these checks only check
  `GreaterEqual` for such nodes.
- `limit_pushdown_missed` trusts the cardinality effect and
  `maintains_input_order`, which do not say that an output row depends on its
  input row only. Windows that need later rows, and custom nodes that look
  ahead or have side effects on the rows they read, are reported, and have
  to allow it, as the audit does for windows.
- `limit_pushdown_missed_at_runtime` and `maintains_input_order_missed`
  report what the generated inputs show, which is not a proof. To avoid
  reporting nodes that only look prefix-closed on the generated data,
  `limit_pushdown_missed_at_runtime` only checks nodes whose cardinality
  effect without their fetch is `Equal` or `GreaterEqual`, so a prefix-closed
  node that reports `Unknown` is not reported. Neither check uses a child
  that reports an ordering or a constant whose order the node does not
  maintain, and
  `maintains_input_order_missed` does not check nodes that report an
  ordering, since sorting keeps sorted input, and rows that tie on the sort
  key, in their input order. A sort on a constant reports no ordering, which
  is why a constant counts as an ordering here. As a result, neither check
  runs in the `uniform constants`, `constants per partition`, `sorted by row id` and `sorted by columns` cases, or above a node that creates a constant.
- `limit_pushdown_missed_at_runtime` and `maintains_input_order_missed` also
  skip a node that can move the rows of a child with several partitions between
  partitions (it computes the statistics of an output partition from the
  overall statistics of the child), since where it puts a row depends on the
  row's values. On generated data such a node can leave every row where it
  is, and look prefix-closed and order preserving: in the `hash partitioned`
  case, the hash `RepartitionExec` between two aggregation phases gets input
  already hash partitioned on the grouping key into as many partitions, and
  in the `constants per partition` case, `RepartitionExec hash preserving order` gets one value of its key per input partition, which hash to
  different output partitions.
- `hash_partitioning_holds` does not check a node over a child whose hash
  partitioning is false, since a node that passes the child's partitioning
  through, as a filter does, has a false one too. Such a node is checked again
  once the child is fixed. A hash partitioning on a key the node does not
  output, which projecting a partitioning marks with an `UnKnownColumn` (as a
  `Partial` aggregate without `GROUP BY` over hash partitioned input does),
  matches no requirement and is not checked.
- `maintains_input_order_holds` cannot track rows through nodes that drop
  the row id column (aggregates, and the audit's `ProjectionExec`s), and does
  not check how rows of several child partitions are interleaved in one
  output partition, which `orderings_hold` checks against the ordering the
  node reports.
- In the `uniform constants` and `constants per partition` cases every
  column of every input is constant, so join keys match every row of the
  other side, or none, and every row of a partition is in the same group.
  The other cases check the plans on varied data. A column that is only
  constant in some inputs, or only some columns that are constant, are not
  generated.
- In the `copied columns` case the only equivalences of the inputs are
  between a column and its copy, which the factory does not know about, so
  they reach a node's output only through nodes that pass the copies on.
  Projections and aggregates in the audit do not, and the union of inputs
  with the same equivalences reports none. Equivalences between columns a
  plan refers to come from its own nodes, such as an inner join on its keys
  or a filter on an equality.
